# OnMap: push, этап 2 (локальная реализация)

Реальная отправка **выключена по умолчанию**. Эта миграция и новые флаги не применялись на VPS. Решение о запуске принимается отдельно после настройки нативных capabilities, APNs/FCM и проверки на устройствах.

## Что работает в коде

- После разрешения уведомлений нативный модуль запрашивает APNs-токен на iOS или FCM-токен на Android; mobile регистрирует или обновляет его через анонимно аутентифицированный `POST /api/push/devices`. При отказе, сбросе identity или смене токена прежнее устройство отзывается/заменяется. Если Firebase-конфигурация Android отсутствует, токен не запрашивается и устройство не регистрируется. Исходный identity ID не пишется в таблицу устройств: хранится отдельный HMAC-ключ. Токен доставки хранится в БД, но не выводится в публичный API и логи.
- Отдельный durable outbox получает одно задание на устройство и метку. Дорожные типы: `ACCIDENT`, `ROAD_CLOSURE`, `ROADWORKS`, `ROAD_HAZARD`; типы не настраиваются пользователем. ДПС в этот список не включён.
- Владелец может создать рекламную кампанию отдельной командой `/partner_push <UUID>` в существующем moderation poller. Только отдельный callback «Подтвердить рассылку» ставит задания в очередь; создание/редактирование точки ничего не рассылает. Частота: не чаще одного подтверждения на точку за 24 часа.
- Worker проверяет актуальность цели перед отправкой, ограничивает отправку устройству, повторяет временные ошибки, отключает недействительный токен. Рекламное задание, пролежавшее в очереди больше 15 минут, отменяется, а не уходит неожиданно после позднего включения доставки. APNs/FCM отправка активируется только при `PUSH_DELIVERY_ENABLED=true` и подходящих файлах credentials. Тестовый `RecordingPushProvider` не подключён к production.
- Нажатие на iOS- или Android-уведомление (или URL `onmap://open/...`) открывает активную метку через адресный GET; отсутствующая/истёкшая метка даёт понятное сообщение. Карточка партнёрской точки получает `promoCode` из публичного API. Холодный и тёплый запуск проверены на уровне JS-тестов; без credentials реальный push-tap не подтверждён.

## Что обязательно сделать перед реальной рассылкой

1. Применить миграцию `20261012150000_add_push_devices_outbox` отдельно от текущей локальной проверки.
2. В Apple Developer включить Push Notifications для реального Bundle ID и подписать сборку подходящим provisioning profile. Entitlements для Debug (`development`) и Release (`production`) добавлены в проект, но без соответствующего App ID/подписи APNs-токен не подтверждён. Проверить его получение и tap на физическом iPhone.
3. Для Android создать/настроить Firebase-проект для реального package name и установить `google-services.json` локально в `android/app/` (файл игнорируется Git). FCM SDK, получение/обновление токена и обработка tap подключены, но без этого файла и тестового устройства их работа не подтверждена. Автоматическая инициализация FCM выключена до разрешения пользователя; Android Debug без Firebase-конфигурации остаётся собираемым.
4. Передать backend key-файл APNs и/или service-account JSON FCM через защищённый read-only mount вне Git. Настроить `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_BUNDLE_ID`, `APNS_ENVIRONMENT`, `APNS_PRIVATE_KEY_FILE` и/или `FCM_SERVICE_ACCOUNT_FILE`; затем отдельно включить `PUSH_ENQUEUE_ENABLED` и `PUSH_DELIVERY_ENABLED`. Ключи не класть в мобильную сборку.
5. Проверить реальные sandbox/production endpoints, invalid-token response, восстановление worker после рестарта и исключить повторную доставку при сбое между провайдером и фиксацией `SENT`. Outbox обеспечивает идемпотентную постановку, но внешняя доставка остаётся at-least-once; APNs/FCM collapse key уменьшает вероятность дубликата, не даёт строгой гарантии.

При локальной проверке никакие запросы к APNs/FCM и Telegram не выполнялись. Ошибки провайдера не логируются целиком, чтобы не вывести токены или закрытые URL.
