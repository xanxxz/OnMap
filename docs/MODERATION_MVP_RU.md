# MVP жалоб и ручной модерации OnMap

Этот документ описывает текущий технический процесс. Это не обещание автоматической проверки каждой жалобы и не юридическое заключение.

## Как работает жалоба

- Пользователь выбирает одну из фиксированных причин в карточке пользовательского события. Свободный текст жалобы не собирается.
- На сервере сохраняется не более одной жалобы от одной anonymous identity на одно событие. Действуют ограничение частоты и запрет автору пожаловаться на собственное событие.
- После десяти жалоб от разных незаблокированных identity событие атомарно скрывается со статусом `HIDDEN_PENDING_REVIEW`; само событие и записи жалоб сохраняются.
- Скрытие доставляется клиентам через Socket.IO и учитывается REST-выдачей. Автор увидит уведомление при следующей загрузке приложения; отдельный push не отправляется.
- Пороговое скрытие не означает, что жалобы истинны. Оно только отправляет дело оператору для ручного решения.

## Закрытая очередь оператора

Очередь доступна только в отдельном Telegram-боте. Backend принимает команды и inline-действия, только если одновременно совпали настроенный private chat ID и Telegram user ID. Публичного moderation endpoint или мобильного входа модератора нет.

Перед настройкой владелец отправляет `/start` созданному боту и запускает из `backend`:

```bash
npm run telegram:moderation-setup
```

Setup-команда выводит только статус и найденный numeric chat ID. Значение нужно вручную добавить в игнорируемый `backend/.env` как `TELEGRAM_MODERATION_CHAT_ID`; токен хранится там же в `TELEGRAM_MODERATION_BOT_TOKEN`. Команда не записывает `.env`. Убедитесь, что `.env` игнорируется Git.

В уведомлении находятся идентификатор дела и события, тип и время создания, число жалоб и агрегат причин, а также actor ID автора, необходимый для ручного ограничения. Исходный текст Telegram и личные данные заявителей не отправляются. Кнопка восстановления возвращает только ещё не истёкшее скрытое событие; ограничение автора доступно на 24 часа, 7 или 30 дней. Автоматического бана по числу жалоб нет.

`/queue` показывает открытые дела. Действия оператора аудируются в БД. Один процесс backend выполняет long polling. Несколько одновременно работающих backend-реплик для одного moderation bot token не поддерживаются без отдельной координации.

Outbox сохраняет уведомление в той же транзакции, что и скрытие события, и повторяет неудачную доставку с задержкой. Telegram Bot API не предоставляет ключ идемпотентности для `sendMessage`: при редком обрыве после принятия сообщения Telegram, но до фиксации ответа в БД, абсолютная exactly-once доставка не гарантируется. Повтор распознаётся по стабильному ID дела в тексте. Не следует трактовать наличие outbox-записи как подтверждение, что оператор уже рассмотрел жалобу.

## Проверки и ручной smoke

Локальные тесты используют mocks и не отправляют сообщения. После успешной настройки владелец может отдельно вручную выполнить:

```bash
npm run telegram:moderation-smoke
```

Команда отправляет в разрешённый private чат одно тестовое сообщение без данных события. Её запуск не является частью автоматических тестов.

Перед применением схемы к окружению развертывания миграция `20260927120000_add_user_generated_content_moderation` должна быть применена штатным процессом миграций. Эта задача не применяет миграцию к production.
