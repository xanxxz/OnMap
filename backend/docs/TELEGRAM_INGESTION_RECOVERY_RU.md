# Восстановление Telegram ingestion

Причина исправления: 16 октября 2026 года на единственном backend был занят MTProto advisory lock и работал HTTP API, но cursor не продвигался около 25 часов. В прежнем коде recovery запускался при старте, замеченном reconnect или следующем live update. Отдельной проверки пропущенных updates не было. Состояние TCP connected и владение lock сами по себе не доказывают доставку сообщений. Конкретная причина прекращения updates внутри прежнего соединения по сохранённым логам не установлена.

Дополнительно воспроизведена ошибка контекста для самостоятельного сообщения «38 актив»: предыдущий вопрос переводил его из REPORT в UPDATE, хотя тип и место уже были в самом сообщении. При отсутствии целевой метки persistence возвращал NOOP. Теперь вопрос сам по себе не меняет самостоятельный REPORT; UPDATE по-прежнему используется, если сообщение действительно наследует тип/место из контекста. Используются существующие alias, координаты и дедупликация. Правила TTL и доверия не меняются.

## Как теперь работает восстановление

- Каждые 30 секунд один supervisor сверяет тот же источник с сохранённым cursor через уже используемый MTProto client. Второй poller или второй backend не создаётся.
- Блок чтения ограничен 200 сообщениями с существующим небольшим перекрытием. При превышении лимита следующая проверка продолжает с подтверждённого cursor. Для этого больше не нужно ждать нового live update.
- Сообщения без текста проходят recovery как пустой вход, который parser игнорирует, но cursor продвигается. Поэтому серия фото без подписей или сервисных сообщений не закрепляет одну и ту же ограниченную страницу перед следующим дорожным сообщением.
- Live-сообщение с пропуском ID сначала запускает сверку: более позднее сообщение не должно перепрыгнуть через потерянное.
- Весь разбор и сохранение проходят через существующую очередь, транзакции и дедупликацию. Cursor не сдвигается вручную и не проходит за сообщение, которое обработалось с ошибкой. Ошибка будет повторяться в безопасном диагностическом логе и сделает health degraded; автоматически пропускать такое сообщение нельзя.
- Сетевая операция ограничена 30 секундами. После трёх ошибок транспорта supervisor завершает старый GramJS client через `destroy()`, затем подключает новый client и подписывает listener, сохраняя MTProto lock.
- Если сверка обнаруживает новые сообщения, а listener их не получал, после периода ожидания supervisor также восстанавливает listener. Проверка сверяет успешность синхронизации, а не возраст последнего поста: тихий источник не считается неисправным.
- Ошибка запуска повторяется с задержками 30, 60, 120, 240 и максимум 300 секунд.
- Зависшая операция без прогресса в течение трёх минут или потеря MTProto advisory lock завершает процесс с кодом 1. Docker `restart: unless-stopped` запускает один контейнер заново. Долгая обработка, во время которой успешно проходят сообщения, не считается зависанием.

## Диагностика

`GET /api/health` проверяет БД и включённый ingestion. Он возвращает HTTP 503 при неполном recovery, ошибке runtime или отсутствии успешной сверки в течение трёх минут. Поля `lastSuccessfulSyncAt` и `lastProcessedAt` используют UTC ISO 8601. Они не содержат Telegram ID, текста сообщения или секретов. У выключенного ingestion статус `disabled`, без ошибки HTTP.

В Docker-логах остаются категория события, решение, причина, результат сохранения и сводный heartbeat каждые пять минут. Текст, source ID, message ID, session и ключи в эти новые записи не входят. Подробные NDJSON не включаются этим исправлением. Логи и health нужно контролировать внешним мониторингом: автоматическая отправка оператору сообщений об авариях не добавлена.

## Что происходит после перезапуска

Существующий cursor загружается из той же БД. Пропущенные сообщения после него последовательно проходят recovery. Дата источника и действующие TTL сохраняются; старое сообщение не становится свежим из-за поздней загрузки. Публичная REST-выдача по-прежнему исключает истёкшие события; правила доверия и условий push не меняются. Для совершенно нового источника без cursor сохраняется прежний baseline последнего сообщения без импорта старой истории как событий.

Это восстановление обработки, а не обещание доставки при недоступной сети или отозванной Telegram session. При отозванной session нужна новая авторизация оператора. Ошибки данных/БД не обходятся сдвигом cursor. Запуск вне Docker требует другого supervisor, который перезапускает процесс после exit 1.

Перед выкладкой нужно сохранить свежий backup и предыдущий образ. Миграций у этого изменения нет. Проверить один backend, два advisory locks, HTTP 200 и свежий `lastSuccessfulSyncAt`; затем проверить решение и сохранение естественного нового сообщения. Не публиковать тесты в рабочий канал и не очищать cursor.

## Проверка исправления 16 октября 2026 года

- Локально: 70 backend suites, 1038 тестов; `tsc --noEmit`, backend build, ESLint изменённых TypeScript-файлов и `git diff --check` прошли. Сценарии потери updates, сетевых таймаутов, повторного подключения, зависания, потери lock и обработки больших страниц проверены тестами с mock-транспортом. Реальное отключение сети на VPS не проводилось.
- Перед обновлениями созданы свежие PostgreSQL backup; `pg_restore --list` подтвердил чтение архивов. Последний backup этого прохода: `/opt/onmap/backend/deploy/vps/backups/onmap-20261016T122756Z-zFqI5m.dump`. Checkpoint исходников и предыдущих образов: `/opt/onmap/deploy-checkpoints/ingestion-supervisor-20261016T121717Z`. Восстановление поверх рабочей БД не запускалось.
- Обновлён только backend-контейнер. PostgreSQL, Caddy, env и миграции не изменялись; статус миграций: 20 применённых, незавершённых нет. Текущий образ: `sha256:7b61af856e1bd3786e11ef7ac64c7d3bdec1b18bf4e62646e110366b6b950f23`.
- Recovery обработал 87 пропущенных сообщений; cursor не сбрасывался. Истёкшие сообщения не получили новый срок жизни. Позднее плановые сверки также обработали естественные изменения источника.
- После финального перезапуска: один healthy backend, по одному владельцу Bot API и MTProto advisory locks, ingestion `RUNNING`. Три последовательные HTTPS-проверки `/api/health` дали HTTP 200 и продвигающийся каждые 30 секунд `lastSuccessfulSyncAt`.
- REST identity, список событий и DPS summary ответили успешно; подключение Socket.IO и подтверждение подписки на город прошли. Это не подтверждает появление новой метки на физическом телефоне. После финального исправления контекста новая подходящая публикация и её появление на устройстве ещё не подтверждены.
- Два сообщения «38 актив», из-за которых началась проверка, к моменту исправления уже вышли за действующий 20-минутный TTL. Они не воскрешались. Исправленный parser проверен на их структуре и предыдущем вопросе без сохранения диагностического события в БД.

Изменения сайта и другие прежние незакоммиченные файлы в этот проход не включались. Мобильная сборка для серверного исправления не требуется. Тестовые сообщения в Telegram и тестовые push не отправлялись.
